- `isLake`'s 8-square lookup table (`board.js:3-6`) matches the official board geometry exactly, and is tested exhaustively for both the 8 lake squares and 4 adjacent non-lake squares (`board.test.js:17-31`), closing off an easy off-by-one class of bug.
- The pure-function design of the whole subsystem (no mutation of input `pieces` arrays; `applyMove` always returns a new `newState` via `state.pieces.map((p) => ({ ...p }))` at `game.js:30`) makes every function here trivially testable in isolation, which is reflected in the test suite's speed and clarity.

2. **(Small)** Add the three missing test cases (Issues #5, #6, #7: `validateMove` ILLEGAL_DESTINATION, Spy-loses-normally, Scout through `getLegalMoves`) to close the coverage gaps identified above.
3. **(Small)** Short-circuit `hasAnyLegalMove` (Issue #3) instead of delegating to `getLegalMoves().length > 0`, since it runs on every move.
4. **(Trivial)** Replace the duplicated Bomb/Flag filter in `game.js:90` with `isMovableRank` (Issue #2).

## Auth & Networking

**Files reviewed:** `web/js/auth.js` (102 lines), `web/js/supabaseClient.js` (31 lines).

**Architecture summary:** This app uses custom JWT auth (username + password, bcrypt hashing and djwt HS256 signing happen server-side in an Edge Function, out of scope for this review) — not Supabase Auth. The Supabase anon key in `supabaseClient.js:8` is intentionally public: per the comment at lines 4-6, there is no RLS policy granting the anon role access to `pieces` or `game_players`, so the key alone cannot read or write game data; every sensitive operation is required to go through an Edge Function or the `get_game_state` RPC. That design is sound as documented. The findings below focus on the client-side token lifecycle, the `callFunction` error-handling path, and the auth UI's use of `innerHTML`.

### Bugs

| # | Severity | Location | Description | Suggested Fix |
|---|----------|----------|-------------|---------------|
| 1 | HIGH | `web/js/supabaseClient.js:12-30` (`callFunction`) + `web/js/auth.js:94-95` (`handleAuthSubmit`) | If `supabase.functions.invoke` ever resolves with `{ data: null, error: null }` (e.g. an Edge Function returns a 2xx with an empty/null body), `callFunction` returns `null` with no validation. `handleAuthSubmit` then calls `saveSession(data.token, data.username)` on that `null`, throwing a `TypeError: Cannot read properties of null (reading 'token')`. This is caught by the generic `catch (err)` at `auth.js:98-101`, which displays `err.message.replace(/_/g, " ").toLowerCase()` — i.e. the user sees the literal, lowercased JS runtime error ("cannot read properties of null (reading 'token')") instead of a meaningful login/signup failure message. | In `callFunction`, after the `if (error)` branch, validate that `data` is non-null (and ideally that it has the shape the caller expects) before returning it; throw a clear `Error` such as `"EMPTY_RESPONSE"` if not. |
| 2 | MEDIUM | `web/js/supabaseClient.js:18-27` | The error-message extraction only falls back to `data?.error` (line 25-26) when `error.context` is absent or `error.context.json` isn't a function (the `else if`). When `error.context.json` *is* a function but resolves to a body with no `.error` field (e.g. the Edge Function's JSON error shape ever uses a different key, or returns `{}`), `message` silently stays at the generic `error.message` (typically Supabase's own "Edge Function returned a non-2xx status code") and `data?.error` is never consulted — even though `data` could contain a more specific message in that case. The two fallbacks are mutually exclusive by construction (`if`/`else if`) rather than layered. | Make the fallback chain cumulative: try `error.context.json()` first, then `errorBody?.error`, then `data?.error`, then `error.message`, in that order, instead of short-circuiting on which branch of the `if`/`else if` is taken. |

### Quality Issues

| # | Severity | Location | Description | Recommendation |
|---|----------|----------|-------------|----------------|
| 1 | HIGH | `web/js/auth.js:31` | `renderNavAuth` interpolates `getUsername()` directly as text content inside a template literal assigned to `navEl.innerHTML`: `` <a ...>${getUsername()}</a> ``. The value is not escaped. The username comes from `data.username` returned by the signup Edge Function (out of scope) and is round-tripped through `localStorage` via `saveSession`. If the server does not strictly whitelist the username charset at signup time, a username such as `<img src=x onerror=alert(1)>` would execute as script in the browser of *that same user* every time the nav bar renders while logged in (and potentially anywhere else in the app that renders usernames the same way, e.g. a profile page, which this review did not check). | 2 | MEDIUM | `web/js/auth.js:4-14` | Neither `getAuthToken` nor `isLoggedIn` ever inspects the JWT's `exp` claim. `isLoggedIn()` only checks that *some* token string is present in `localStorage`. A user whose token has expired server-side still appears logged in (nav shows their username and a "Log out" button) until the next authenticated `callFunction` call fails — and that failure isn't given any special handling (no distinction between "expired token" and any other error), so the user has no clear signal that they need to log in again. | Decode the token's `exp` (or have the server include an expiry alongside the token at login/signup) and have `isLoggedIn()` / a periodic check treat an expired token as logged-out, clearing the session and prompting re-auth with a specific message. |
| 3 | LOW | `web/js/auth.js:99` | `errorEl.textContent = err.message.replace(/_/g, " ").toLowerCase()` assumes every error reaching this `catch` is an `Error` whose `.message` is an upper-snake-case server error code (e.g. `INVALID_PASSWORD` → "invalid password"). That assumption holds for errors thrown deliberately by `callFunction`, but not for the `TypeError` described in Bug #1, a failed dynamic `import()` (line 93), or any other unexpected JS exception — those messages have no underscores to strip and get shown to the user verbatim (just lowercased), leaking internal implementation details instead of a clean user-facing message. | Distinguish "known" error-code exceptions (from `callFunction`) from unexpected exceptions, and show a generic fallback message ("Something went wrong — please try again") for the latter instead of the raw lowercased exception text. |
| 4 | LOW | `web/js/supabaseClient.js:14` | `callFunction` unconditionally merges `authToken` into the body of every call once a token exists in `localStorage`, with no allowlist of which function names expect it. ### Positive Observations

- The anon-key design is sound: pairing a public, unrestricted-looking key with the absence of any RLS grant is the correct way to safely ship a "public" Supabase key — all sensitive reads/writes are forced through Edge Functions, which is exactly what the comment at `supabaseClient.js:4-6` claims.
- The token/session storage surface is small and consistent — two `localStorage` keys and four tiny accessor functions (`getAuthToken`, `getUsername`, `isLoggedIn`, `saveSession`, `logout`) — which makes the whole client-side session model easy to read and audit in one pass, even though `localStorage` carries the standard XSS-exposure trade-off noted in Quality Issue #1.
- `callFunction` always throws a real `Error` object on failure (never a bare string or plain object), which keeps the `catch (err) { err.message... }` contract in `auth.js:98-99` consistent and avoids a whole class of "`undefined` is not a function" bugs that `throw "some string"` patterns tend to invite elsewhere.
- There is no realistic CSRF exposure given this architecture: auth state lives in `localStorage`, not a cookie, and the token is read explicitly by JS and attached to the request body (`supabaseClient.js:13-14`) rather than sent ambiently by the browser. A cross-site request can't replicate that without already having XSS-level access to the page, so classic cookie-based CSRF doesn't apply here — a reasonable design choice given the custom-JWT approach.
- Passwords are sent in the request body over HTTPS with no client-side hashing or weakening transformation (`auth.js:94`) — correct behavior; client-side password hashing before TLS is a common anti-pattern this code correctly avoids, leaving all password handling (bcrypt) to the server as intended.

### Recommendations

1. **(Small)** Fix the null-`data` crash path in `callFunction` (Bug #1) — validate `data` before returning it, so a malformed/empty Edge Function response produces a clear error instead of a leaked `TypeError` message in the UI.
2. **(Small)** Make the error-message fallback chain in `callFunction` cumulative instead of `if`/`else if` exclusive (Bug #2), and give `handleAuthSubmit`'s catch block a generic fallback message for non-`Error`/unexpected exceptions so raw JS error text never reaches the error UI (Quality Issue #3).
3. **(Small)** Escape or switch to `textContent` for the username interpolated into `innerHTML` in `renderNavAuth` (Quality Issue #1) — the highest-leverage fix here, since it's a plausible stored-XSS vector regardless of what server-side validation turns out to do.
4. **(Medium)** Add client-side JWT expiration awareness (Quality Issue #2) so a stale session is detected proactively rather than discovered only when an authenticated call happens to fail.

### Positive Observations

- The room code and invite URL rendered into `innerHTML` at `home.js:21-30` are *not* an injection vector despite the brief's concern: `roomCode` is always generated server-side from a fixed, whitelisted alphabet (`ROOM_CODE_CHARS = "ABCDEFGHJKMNPQRSTUVWXYZ23456789"`, `create-game/index.ts:8`) with no HTML metacharacters possible, and the client never accepts a room code from anywhere except that response or a URL/localStorage round-trip of the same value. This is a case where the architecture (server-controlled, charset-restricted identifiers) closes off a risk the UI code alone wouldn't obviously rule out.
- The `storeSession`/collision concern the brief raised is also resolved by the schema, not the client: `room_code` is declared `unique not null` (`migrations/0001_init.sql:6`), and `create-game` retries up to 5 times on a `23505` (unique-violation) error (`create-game/index.ts:45-55`) rather than ever allowing two live games to share a code — so two different tokens can never silently collide under the same `storeSession` key while both games are live, and there's no code path that frees/reuses a room code for a finished game.
- The three "start a game" entry points (new game, join, play-vs-bot) are each a short, self-contained `addEventListener` block with a consistent try/catch/(finally) shape — easy to scan top-to-bottom and compare against each other, which is exactly how this review was able to spot that two of the three disable-then-reenable their button but only one (`play-bot-btn`) leaves it disabled after an error that also happens to leave `gameId` orphaned.
- `maxlength="8"` on both the join and spectate room-code inputs (`index.html:33,41`) is not an arbitrary guess — it matches `ROOM_CODE_LENGTH = 8` server-side (`create-game/index.ts:9`) exactly, so the client-side constraint, while not a substitute for server validation, isn't misleading users about the actual code format.

### Recommendations

1. **(Small)** Guard `refreshGameRow`'s assignment at line 90 against out-of-order responses using `turn_number` (Bug #1) — the highest-priority fix in this section, since it's the one finding that can leave the rendered game state genuinely incorrect (not just stale) until the next lucky refresh.
2. **(Small)** Reorder or merge `refreshState`/`refreshMoveLog`'s render calls so the graveyard/board are never painted from last cycle's `lastMoveData` (Bug #2) — removes the recurring flicker and the secondary risk it creates for Bug #5.
3. **(Small)** Add an in-flight guard to `handleCellClick`'s move-submission branch (Bug #3) to stop a rapid second click from firing a concurrent `make-move` call.
4. **(Medium)** Index `piecesById` by `"row,col"` and stop rebuilding the entire board DOM on every render (Quality Issues #2-#3) — the single highest-leverage performance fix, especially combined with eliminating the double-render (Quality Issue #1).
5. **(Small)** Surface a visible "connection issue" state when `refreshState` fails (Bug #4) instead of a silent `console.error`.
6. **(Small)** Persist the "bot couldn't find a legal move" state instead of letting the next routine refresh silently clear it (Bug #6).
7. **(Trivial)** Delete the unused `RANK_SHORT` constant (Quality Issue #7); add the static-label render guard already used in `setup.js` (Quality Issue #5); add backoff to `makeBotMove`'s retry loop (Quality Issue #4).

### Positive Observations

- Where coverage exists, it is unusually thorough and already follows the project's own hard-won lesson about identity-based assertions: `pieceMemory.test.js` and `pieceSuspicion.test.js` both include dedicated "jitter boundary" tests that pin exact threshold values with an injected deterministic seed function (e.g. `findSuspects(..., 'hard', 7, () => 0)` asserting the boundary is crossed at turn 7, not merely "eventually true") — this is a notably higher bar than typical boundary testing and would have caught subtle off-by-one errors in the jitter math had any existed.
- `flagDefense.test.js`'s `assessGuardSquares` tests enumerate every status transition (`open`, `safe`, `atRisk`) across every triggering condition (empty neighbor, known-safe guard, known-dangerous enemy, unrevealed enemy via rank estimate, off-board corner, lake-adjacent, breached-by-enemy, outside-radius, exact-tie-still-atRisk) — 10 tests covering what is effectively a 2D decision table, with no gaps found in this review.
- `twoSquareRule.test.js` (already praised in the Rules Engine section) and `bot.test.js`'s own row-mapping regression test (Bug #1 aside) both demonstrate the project *knows* how to write a precise regression test when a real historical bug motivates one — the gap identified here is one of *coverage breadth* (which modules get this treatment) and *maintenance* (keeping the assertion in sync with the fix), not of testing skill or technique.
- `chooseBotMove`'s 20 tests collectively exercise a wide behavioral surface — winning-capture preference, losing-capture avoidance, forced losing captures, remembered-but-fogged ranks, guard-square vacate/reinforce logic, and three distinct bot personalities — for a 182-line file, this is close to one test per meaningfully distinct decision branch, which is a good ratio for AI/heuristic code that's otherwise hard to verify by reading alone.

### Missing Test Categories (ranked by impact)

1. **`setup.js`'s row/column mapping (no tests at all).** This is the single highest-priority gap. It is the exact logic responsible for the project's most expensive bug class — found twice independently (`setup.js` itself in 2026-07-11, then the parallel `bot.js` copy in 2026-07-12) — and the one test that exists for the sibling implementation (`bot.test.js`) is currently failing (Bug #1). Per PROJECT_MEMORY's own stated lesson, any new test here must assert piece *identity* (e.g. "the Flag's local back-row cell lands on absolute row 9 for slot 1, row 0 for slot 2, not just any row 6-9/0-3") and column side (for slot 2's mirror), not just aggregate range/count checks.
2. **Fix the stale `bot.test.js` assertion (Bug #1) before adding anything else.** A currently-failing regression test for exactly this bug class is strictly worse than having no test at all, because it consumes the "red means look closely" signal that the rest of the suite depends on.
3. **`make-move` Edge Function — zero tests, 6-for-6 historical bug concentration.** While technically outside `web/js/`, this is the most bug-dense file in the project's entire history and the only one of the 14 Edge Functions with meaningful logic (transactional writes, win-condition checks, move validation orchestration) that has no corresponding `.test.ts` file, unlike `information-warfare.ts` in the same directory.
4. **`formations.js`'s 5,745-line formation catalog — no structural validation.** `bot.test.js:23-40` already proves the pattern needed (full army, no duplicate squares, correct per-rank counts, no lake squares) for the bot's *generated* placements; the same checks have never been run against the human-authored formation catalog itself, which is both much larger and hand-edited (more failure-prone) than anything the bot generates on the fly.
5. **`game.js`'s graveyard rendering (`renderGraveyards`/`renderSingleGraveyard`, lines 367-467) and board rendering — zero tests on the file most central to actual gameplay.** No integration-style test exists anywhere in the suite that exercises more than one module together (e.g. `applyMove` → `renderGraveyards`, or `chooseBotMove` → `applyMove` for a full bot turn); every current test is a narrow unit test of a single pure function. A single "play N bot-vs-bot moves and assert the game reaches a valid terminal state" integration test would catch a wide class of cross-module regressions that today's 107 passing unit tests structurally cannot.

### Recommendations

1. **(Trivial, do first)** Fix the stale assertion in `bot.test.js:17-20` (Bug #1) to match the intentional column-mirror behavior, and add one new assertion locking in the mirror itself. This single fix turns "2 failures, unclear which matter" back into a trustworthy signal.
2. **(Small)** Separate the Node and Deno test commands (Quality Issue #1) — either glob `node --test` to `test/` only, or wire up a combined `npm test` that runs both runners — so `0 failures` becomes an achievable, meaningful state again.
3. **(Small)** Extract `setup.js`'s row/column mapping into a testable pure function and write identity-based tests for both slots and both axes (Quality Issue #3 / Missing Category #1) — the highest-leverage net-new test in the project given its bug history.
4. **(Medium)** Add a structural-validation test for `formations.js`'s full catalog (Missing Category #4), reusing the exact pattern `bot.test.js:23-40` already established for bot-generated placements.
5. **(Medium)** Add at least minimal coverage for `make-move`'s transactional write-ordering logic (Missing Category #3) and one cross-module integration test exercising a full simulated turn (Missing Category #5) — both are larger efforts than the others here, but address the two biggest structural blind spots (Edge Function logic, and multi-module interaction) that no amount of additional unit testing on already-covered pure functions would close.
